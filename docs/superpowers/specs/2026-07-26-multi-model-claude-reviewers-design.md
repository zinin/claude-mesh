# Design — мультимодельные Claude-ревьюеры

**Дата:** 2026-07-26
**Тема:** multi-model-claude-reviewers
**Статус:** утверждён в brainstorming, готов к writing-plans

---

## 1. Контекст и проблема

`/claude-mesh:mesh-review` и `/claude-mesh:mesh-design-review` запускают набор ревьюеров:
встроенный `claude`, обёртки над внешними CLI (`codex`, `gemini`) и `ext-claude` на моделях из
секции `models:` конфига.

Модель, на которой исполняется **встроенный** `claude`-ревьюер, задаётся глобальным ключом
`runtime.dispatch_model` (`commands/mesh-review.md:151`, правило **Dispatch model**): при непустом
значении к каждому Task-диспатчу добавляется `model: "<значение>"`, при пустом — модель
наследуется от сессии.

Отсюда два ограничения.

**(1) `dispatch_model` — один рубильник на четыре разные вещи:**

| Что задаёт `runtime.dispatch_model` | Значимость |
|---|---|
| модель встроенного `claude`-ревьюера | определяет качество ревью |
| модель обёрток codex / gemini / ext-claude | почти не важна: обёртка лишь запускает внешний CLI |
| модель агента `review-discussion` | важна для качества разбора замечаний |
| модель сабагентов `/do-plan` | важна, но это другой сценарий |

Переключить ревью на другую модель нельзя, не переключив заодно всё остальное.

**(2) `builtin: [claude]` — ровно один ревьюер.** Запустить независимые ревью на двух Claude-моделях
(например `opus` и `fable`) параллельно, а затем разобрать их результаты в основной сессии,
невозможно.

**Сопутствующий баг.** Валидатор принимает `claude` в `defaults.design_review.builtin`
(`skills/shared/config-loader.sh:377`), но `skills/mesh-design-review/SKILL.md:253-256` (Step 5.1)
раскрывает только `codex` → `codex-executor` и `gemini` → `gemini-executor` — ветки для `claude`
нет. В интерактивном Q1 (Step 5.2) опции `claude` тоже нет. Итог: **design-review никогда не
запускал Claude-ревьюера**, значение молча проглатывается.

---

## 2. Цель

Дать возможность запускать **несколько независимых Claude-ревьюеров на разных моделях** в рамках
одного прогона `/mesh-review` и `/mesh-design-review`, независимо от модели основной сессии и от
`runtime.dispatch_model`. Основная сессия при этом остаётся оркестратором: она агрегирует
результаты, классифицирует замечания и вносит правки.

Целевые сценарии (все должны работать):

- сессия на `opus`, ревью на `opus` + `fable`;
- сессия на `fable`, ревью только на `opus`;
- сессия на любой модели, ревью на `opus` + `fable` + внешние модели + codex.

Попутно — починить `claude` в design-review.

## 3. Схема конфига

### 3.1. Новая секция `claude:` — каталог моделей

```yaml
claude:                        # [optional] конфигурация встроенного claude-ревьюера
  models: [opus, fable]        # [optional] каталог Claude-моделей, предлагаемых в UI
```

Значения — то, что принимает параметр `model:` Task-тула: `opus | sonnet | haiku | fable` и любой
id, поддерживаемый конкретной сборкой Claude Code. Каталог — плоский список строк: подписи
(`label`) не нужны, алиас самодостаточен.

**Асимметрия с `codex:` / `gemini:`, которую документируем явно.** Те секции — гейты: если секции
нет, `builtin: [codex]` даёт ошибку валидации. Секция `claude:` гейтом **не является**: `claude` —
единственный builtin без внешних зависимостей, он работает и без секции. `claude:` лишь расширяет
его до мультимодельного.

### 3.2. Новый ключ пресетов `claude_models`

```yaml
defaults:
  code_review:
    builtin: [claude, codex]
    claude_models: [opus, fable]     # ★ в UI + что запускает `default`
    models: [zai/glm, ...]
    run_mode: background
  design_review:
    builtin: [claude, codex]
    claude_models: [opus]            # может отличаться от code_review
    models: [zai/glm, ...]
```

Каждый элемент `claude_models` обязан присутствовать в каталоге `claude.models` — та же связь,
что между `defaults.*.models` и `models[].id`.

## 4. Семантика раскрытия

| `claude` в `builtin` | `claude_models` в пресете | Что запускает `default`-режим |
|---|---|---|
| нет | — (неважно) | claude-ревьюеров нет |
| да | не задан / `[]` | **1 ревьюер**: `model: "<dispatch_model>"`, а если тот пуст — без `model:` (наследует модель сессии). Ровно сегодняшнее поведение |
| да | `[opus, fable]` | **2 ревьюера**: `model: "opus"` и `model: "fable"`; `dispatch_model` на них не влияет |

Строка 2 — сознательное решение в пользу строгой обратной совместимости: появление секции
`claude:` в конфиге **не меняет** поведения существующих пресетов, пока в пресет явно не добавлен
`claude_models`. Альтернатива («нет `claude_models` ⇒ берём весь каталог») отвергнута: она молча
превращает одного ревьюера в N и умножает расход токенов.

**Интерактивный режим:** каталог задаёт список опций; `claude_models` пресета задаёт, на каких
стоит ★. Если пользователь не выбрал ни одной модели на странице выбора — применяется то же
fallback-правило (1 ревьюер).

`runtime.dispatch_model` сохраняет прежний смысл для всего остального: обёрток codex / gemini /
ext-claude, агента `review-discussion` и сабагентов `/do-plan`.

## 5. Валидация

Новая функция `validate_claude()` в `skills/shared/config-loader.sh` — стилистически копия
`validate_codex` (`config-loader.sh:262-317`): type-dispatch gate, затем charset, **без enum**.
Встраивается в `validate_all()` между `validate_gemini` и `validate_defaults` — порядок важен,
`defaults` ссылается на каталог.

### 5.1. `claude:` / `claude.models`

| Условие | Результат |
|---|---|
| `claude:` — не mapping и не `null` (например `claude: false`) | die: `claude: must be a mapping with a models key (got <type>)` |
| `claude.models` — не список и не `null` | die: `claude.models: must be a list, got <type>` |
| `claude.models` отсутствует или `[]` | каталога нет, ошибки нет |
| элемент не строка | die |
| элемент не матчится `IDENT_RE` (`^[A-Za-z0-9][A-Za-z0-9._:@-]*$`) | die |
| дубликат в каталоге | die |

`IDENT_RE` — тот же регексп, что у `runtime.dispatch_model` (`config-loader.sh:57`). Enum моделей
не вводится: это принципиальное правило проекта (forward-compat — новая модель не должна требовать
релиза плагина). Неизвестное имя ловится не валидатором, а падением диспатча.

Дубликаты запрещены, потому что два ревьюера с одинаковым именем неразличимы в дедупликации
и в таблицах атрибуции.

### 5.2. `defaults.<preset>.claude_models`

Проверяется в `validate_defaults()`, которая вызывает `validate_claude` **сразу после проверки
наличия `.defaults` и до чтения каталога** — дёшево, идемпотентно и гарантирует, что каталог уже
корректный список, прежде чем проверять членство.

Именно после early-return, а не «первым делом»: если секции `defaults:` нет, каталог не читает
никто и валидировать его незачем. Это то же расслоение, что уже действует для `models:` —
`validate_defaults` ссылается на `.models`, но `validate_models` не вызывает (зафиксировано
комментарием в `config-loader.sh`), и `get-defaults` на конфиге с `models: false` без `defaults:`
возвращает пустой пресет с rc=0. Делать `claude:` строже, чем `models:`, было бы необъяснимой
асимметрией.

Настоящая причина вызова — защита следующей же строки, а не строгость как таковая: `.models`
лежит на верхнем уровне и прикрыт оператором `//`, тогда как `(.claude.models // [])` сначала
индексирует `.claude`, и на скаляре это падает с `Cannot index boolean` до того, как `//` успеет
сработать. Битая `claude:` при этом всё равно не проходит незамеченной: её ловят `validate` и обе
команды каталога (`get-flag has_claude_models`, `list-claude-models`), каждая из которых
валидирует секцию сама.

| Условие | Результат |
|---|---|
| не список и не `null` | die: `defaults.<preset>.claude_models: must be a list, got <type>` |
| элемент не строка | die — симметрично §5.1. Без этой проверки `jq -r` приводит число/булево к строке, и каталог `["5","true"]` принял бы пресет `[5, true]`. Сюда же попадает ловушка YAML 1.1: некавыченный `[yes]` парсится как boolean |
| элемент — пустая строка | die: `defaults.<preset>.claude_models[i]: empty value`. Проверка **обязана** предшествовать проверке членства: при отсутствующем каталоге строка сравнения вырождается в два пробела, и glob пустого значения матчится с ней — пустой элемент прошёл бы членство вообще без каталога |
| элемент отсутствует в каталоге `claude.models` | die: `defaults.<preset>.claude_models[i]: unknown claude model "<v>"` |
| `claude_models` непуст, а каталога нет | die (частный случай предыдущей строки — сообщение должно подсказывать добавить секцию `claude:`) |
| дубликат в `claude_models` | die |
| `claude_models` непуст, но `claude` отсутствует в `builtin` того же пресета | die: `defaults.<preset>.claude_models is set but "claude" is missing from defaults.<preset>.builtin` |

Последнее правило — fail-closed: такая конфигурация почти наверняка опечатка, а молча
проигнорированный список — ровно тот класс ошибки, который сейчас есть в design-review.

Тексты `die` пишутся по-английски — как все остальные сообщения валидатора в `config-loader.sh`.

## 6. Изменения в `config-loader.sh`

### 6.1. Новые подкоманды

| Команда | Вывод | Валидирует |
|---|---|---|
| `get-flag has_claude_models` | `1` / `0` — каталог непуст | `validate_claude` |
| `list-claude-models` | по одному id в строке, порядок конфига | `validate_claude` |

`list-claude-models` печатает **только id**, без `|label`, — в отличие от `list-models`. Отличие
фиксируется в usage-строке. Если позже понадобятся подписи, каталог обратносовместимо расширяется
до списка объектов `{id, label}`.

Обе команды валидируют свою секцию — по принципу typed-getter'ов (`dispatch_model`,
`do_plan_default_stop_tokens`), а не по принципу `has_codex` / `has_gemini` (те — чистые проверки
существования секции, без чтения внутрь). Причина: обе новые команды читают *внутрь* секции, и на
`claude: false` голый `jq` упал бы с `Cannot index boolean`.

`get-flag`-diagnostics (`config-loader.sh:685`) и usage-строка (`config-loader.sh:795`) обновляются
списком допустимых значений.

### 6.2. Изменённые подкоманды

`get-defaults <category>` — в JSON добавляется поле `claude_models`:

```json
{"builtin":[...],"claude_models":[...],"models":[...],"run_mode":...}
```

`get-runtime` не меняется.

## 7. Изменения в `/mesh-review` (`commands/mesh-review.md`)

### Step 0 (`default`-режим)

Из `get-defaults code_review` дополнительно читается `.claude_models`; claude-ревьюеры
раскрываются по таблице из §4.

### Step 1 (интерактив)

Добавляются чтения `HAS_CLAUDE_MODELS=$("$LOADER" get-flag has_claude_models)` и
`CLAUDE_MODELS=$("$LOADER" list-claude-models)` — тем же rc-aware способом, что остальные чтения
в этом шаге.

### Step 2 (Q1, типы ревьюеров)

Без изменений: опция `claude` показывается всегда, ★ если она есть в `defaults.code_review.builtin`.

### Новый Step 2.4 — страница выбора Claude-моделей

Встаёт между Q1 (типы) и Step 2.5 (подтверждение типов).

- Показывается только если в Q1 выбран `claude` **и** `HAS_CLAUDE_MODELS=1`.
- Если `claude` в Q1 **не** выбран — шаг пропускается и claude-ревьюеров нет вообще, независимо от
  каталога.
- Если `claude` выбран, но каталог пуст (`HAS_CLAUDE_MODELS=0`) — шаг пропускается и действует
  fallback (1 ревьюер).
- AskUserQuestion, `multiSelect: true`, пагинация по 4 — та же механика, что Step 3.
  ★ на моделях из `defaults.code_review.claude_models`.
- Пустой выбор → fallback, 1 ревьюер.

Почему именно здесь: выбор Claude-моделей — часть ответа на вопрос «кто ревьюит», поэтому его
подтверждает уже существующий Step 2.5, где список выглядит как `claude:opus`, `claude:fable`,
`codex`, `external models`. Третье подтверждение не добавляется; «Нет, выбрать заново» на Step 2.5
перезапускает и Q1, и новую страницу (существующий cap в 3 попытки сохраняется).

### Step 5a / 5b (диспатч)

На каждую выбранную Claude-модель — отдельный Task: `subagent_type: "general-purpose"`,
`model: "<модель>"`, промпт вызывает `superpowers:requesting-code-review` (как сейчас). В
fallback-случае — один Task с `model: "<DISPATCH_MODEL>"`, а при пустом `DISPATCH_MODEL` — без
`model:`.

Правило «claude-ревьюер не обёртка и в список `engine:model` для verify-delegation не попадает»
сохраняется — теперь во множественном числе. В disk-watch/ping-цикле claude-ревьюеры не участвуют:
run-dir не создают, завершаются сами.

### Step 6.0 (таблица делегирования)

Сейчас claude-ревьюер молча пропускается. Когда их несколько, таблица должна быть полным списком
участников, поэтому добавляются информационные строки:

```
| Reviewer            | Verdict | Action              |
|---------------------|---------|---------------------|
| claude:opus         | INLINE  | ✅ по построению     |
| claude:fable        | INLINE  | ✅ по построению     |
| ext-claude/zai/glm  | REAL    | ✅ kept              |
```

`INLINE` — не вердикт `verify-delegation.sh`, а метка «проверка делегирования не применяется по
построению», проставляемая оркестратором. Скрипт `verify-delegation.sh` не меняется и для
claude-ревьюеров не вызывается. Строка добавляется и в fallback-случае — тогда она одна и
называется просто `claude`.

### Step 6.1 (дедупликация и классификация)

В колонке «Кто нашёл» фигурируют `claude:opus` / `claude:fable`. Замечание, найденное двумя разными
Claude-моделями, — подтверждение находки, ровно как совпадение codex и ext-claude.

## 8. Изменения в `/mesh-design-review` (`skills/mesh-design-review/SKILL.md`)

Помимо новой функциональности здесь чинится баг из §1.

### Step 5.0

Добавляются чтения `has_claude_models` / `list-claude-models`. `DEFAULTS_JSON` уже читается и
теперь содержит `.claude_models`.

### Step 5.1 (`default`-режим)

Добавляется отсутствующая ветка `claude` в раскрытии `.builtin` — исправление бага. Раскрытие
по таблице из §4.

### Step 5.2 (Q1)

Добавляется опция `claude`, показываемая всегда (как в `/mesh-review`), с ★ если она есть в
`defaults.design_review.builtin`. Существующая ветка «если ничего не доступно — STOP» становится
недостижимой и заменяется явной формулировкой: `claude` доступен всегда, секции в конфиге не
требует.

### Новый Step 5.2.5

Страница выбора Claude-моделей, идентичная Step 2.4 из `/mesh-review`. Здесь проще: у
design-review одно подтверждение (Step 5.4), которое и так показывает весь набор.

### Step 6 (диспатч)

Claude-ревьюер получает composed prompt из Step 4 **напрямую**, без обёртки
`Execute this prompt via…`: этот промпт самодостаточен (задача, документы, контекст проекта и
сессии, PREVIOUS DECISIONS, фокус ревью, формат вывода). Параметры Task:
`subagent_type: "general-purpose"`, `model: "<модель>"`,
`description: "Design review via claude:opus (iter N)"`.

Явно фиксируется: claude-ревьюеры **исключены** из disk-watch/ping-цикла — run-dir не создают и
завершаются сами. Без этой оговорки контроллер будет ждать возможности «пингнуть» агента, который
уже всё вернул.

### Step 7 (merge)

По секции на ревьюера: `## claude:opus`, `## claude:fable`.

### Прочее

Выбор набора, как и сейчас, делается на первой итерации и переиспользуется во всех последующих.

## 9. Именование и атрибуция

Каждый claude-ревьюер везде фигурирует как `claude:<model>`:

- список запускаемых ревьюеров при диспатче;
- подтверждающие вопросы UI;
- колонка «Кто нашёл» в таблице классификации;
- таблица делегирования Step 6.0;
- заголовки секций merged-файла design-review.

Единственный ревьюер в fallback-случае остаётся просто `claude`.

## 12. Границы объёма

Не меняется:

- `/do-plan` — сабагенты продолжают ходить на `runtime.dispatch_model`;
- агент `review-discussion` — тоже на `dispatch_model`;
- `codex:` / `gemini:` — по одной модели, мультимодельность им не добавляется;
- `runtime.dispatch_model` не переименовывается и не делится на несколько ключей;
- `verify-delegation.sh` — не меняется.

## 13. Известные ограничения

Проверить постфактум, что сабагент **реально** исполнился на запрошенной модели, невозможно:
оркестратор не видит метаданных Task, а спрашивать саму модель «кто ты» ненадёжно. Механического
guard'а уровня Step 6.0 здесь не будет и быть не может. Опора на то, что неподдерживаемое имя
модели роняет диспатч с ошибкой (уже зафиксировано в `README.md:54`), а не подменяется молча.

Практическое следствие: значения в `claude.models` должны быть теми, что принимает параметр
`model:` Task-тула данной сборки Claude Code. Полные облачные id (Bedrock / Vertex) валидатор
пропустит по charset, но диспатч может их не принять.

## 14. Отвергнутые альтернативы

**Кодировать модель прямо в `builtin`:** `builtin: [claude:opus, claude:fable, codex]`. Отвергнуто:
`builtin` превращается в мини-DSL, а каталога для интерактивного UI всё равно нет — предлагать в
UI было бы нечего, кроме того, что уже прописано в пресетах.

**Каталог без пресетного уровня** (`claude.models` — одновременно каталог и default-набор).
Отвергнуто: `default`-режим тогда всегда запускает *все* модели каталога, разные наборы для
code_review и design_review невозможны, а ★-пометка в UI вырождается (звёздочка на всём).

**Пресеты без каталога** (UI предлагает объединение `defaults.*.claude_models`). Отвергнуто: чтобы
модель просто *появилась* в списке UI, её надо занести в пресет — и она немедленно становится
★-рекомендованной. Разделение «доступно / рекомендовано» ломается.

**Claude-модели как псевдо-провайдер в существующей секции `models:`** (`provider: claude-native`).
Отвергнуто: ломает инвариант `<provider>/<short>` с обязательной записью в `providers:` и тянет
спецслучаи в export-путь ext-claude, run-dir'ы и `verify-delegation.sh`.

**Enum допустимых Claude-моделей в валидаторе.** Отвергнуто: противоречит принятому в проекте
принципу forward-compat (см. `runtime.dispatch_model` и `codex.reasoning_level`) — новая модель
не должна требовать релиза плагина.
